# Household Allocation Design

このドキュメントは、家事按分（経費の事業使用分と家事使用分の区分）をどのレイヤーで扱うかと、その登録ルールを整理したものです。

ここでいう「家事按分」は、水道光熱費・地代家賃・通信費などの支出のうち、事業割合分だけを経費として帳簿に計上する処理を対象にする。

## 目的

- 按分を取引ごとに設定でき、入力時に適用し、後から修正できるようにする
- 予定取引（`is_planned = true`）にも按分を効かせ、経費・収入の見通しを事業分ベースで立てられるようにする
- 月ごとに按分割合が変わる運用を許容する
- 既存および将来の集計サービス（サマリー・元帳・試算表・消費税集計）に按分を意識させない

## 基本方針

按分は「集計時に割合を掛ける」方式ではなく、「登録時に仕訳を実分割する」方式とする。

- 入力時に事業割合を受け取り、経費行を「経費（事業分）」と「事業主貸（家事分）」の 2 行に分割して保存する
- 帳簿（元帳・集計）は登録時点で常に正しい金額になる
- 決算時の一括振替仕訳は作らない
- 集計サービス側の按分対応は一切不要とする

```
例: 電気代 10,000 円（税込）、事業割合 60%

借方: 水道光熱費 6,000（事業分）
借方: 事業主貸   4,000（家事分）
貸方: 現金     10,000
```

### 集計時掛け算方式を採らない理由

`Transaction` に割合だけを持たせて集計時に経費 × 割合で減額する方式は採用しない。

- すべての集計サービスが按分を意識する必要が生まれ、掛け忘れが帳簿と申告のズレに直結する
- 元帳上の経費が全額のままになり、簿記として不正確になる

### 決算時一括振替方式を採らない理由

- 予定取引の集計が全額経費のままになり、期中の見通しが過大に出る
- 月ごとの割合変更を年次の一括計算で表現しにくい
- 月次締めで振替仕訳の生成・再生成が必要になり、締め処理が重くなる

登録時分割であれば、月次締めは仕訳を生成しない検証だけのオペレーションにできる（月次締め自体は別ドキュメントで扱う）。

## 割合の保持

正式な帳簿データとして割合を持つのは `Transaction` ではなく `JournalEntry`（分割後の経費行）とする。

想定する追加項目は次の通り。

- `journal_entries.business_ratio`
  - 事業割合（%、整数）
  - 分割後の「事業分の経費行」に付く
  - カラムは `nullable` とし、DB デフォルトは `null` とする
  - `1〜100` を許可する
  - 100% 事業経費として処理した行も、`business_ratio = 100` を保持する
- `journal_entries.allocation_group_id`
  - 1 つの按分入力から生成された行群を束ねる識別子
  - 事業分の経費行と家事分の `事業主貸 / 家事按分` 行に同じ値を付ける
  - 按分していない行は `null`

`Transaction` に割合カラムは追加しない。

- 1 取引に按分対象の経費行が複数入る場合（家賃と駐車場を 1 回の振込で払う等）、行ごとに割合が異なりうる
- 割合を 2 箇所に持つと、修正時に不整合が生じる

`allocated_from_journal_entry_id` のような行間 FK は持たない。

- `TransactionRegistrar` は入力正規化の時点では `journal_entries.id` をまだ持っていない
- 保存順序に依存する相互参照を避け、1 パスで正規化・保存できる形を優先する
- 「どの事業分行とどの家事分行が 1 組か」は `allocation_group_id` で表現する

`business_ratio` の `null` と `100` は意図的に使い分ける。

- `null`
  - 按分機構を通っていない行
  - 例: 貸方行、収益行、`net_amount` 直接入力の経費行、既存データ
- `100`
  - 按分機構を通った結果、全額事業経費と判断された借方経費行

したがって、既存の経費行を一律に `100` へ埋める移行は行わない。

### `allocation_group_id` の仕様

- 型は UUID とする
- 発行責務は `TransactionRegistrar` とし、按分展開時に生成する
- 実装上は全体一意だが、意味としては「同一取引内で同じ按分入力から生成された行群」を表す
- 1 取引内に複数の `allocation_group_id` が共存してよい
- 復元・表示でグループ検索に使うため、マイグレーションでは index を張る

### グループ内の識別規約

同一 `allocation_group_id` を持つ行のうち、各行の意味は次の規約で判定する。

- `business_ratio != null` の借方経費行が「事業分行」
- `business_ratio == null` かつ `sub_account_id = householdAllocationSubAccountId` の借方行が「家事分行」

ここで `householdAllocationSubAccountId` は、`事業主貸 / 家事按分` 補助科目の ID を指す。

補助科目名そのものは判定規約には使わない。名前ではなく `sub_account_id` を正とし、補助科目の選択は不変条件として保証する。

この規約により、後から

- 元の総支払額
- 事業分として経費算入した額
- 家事分として除外した額

を機械的に復元できるようにする

あわせて、次を不変条件とする。

- 家事分行の補助科目は必ず `事業主貸 / 家事按分`
- 1 つの `allocation_group_id` には、事業分行 1 行と家事分行 1 行だけを属させる

取引単位の表示用途には、`getTotalAmountAttribute()` と同様に `journalEntries` から導出するアクセサを用意する。

- 全按分対象の経費行が同率ならその値、混在なら `null` を返す `Transaction::getBusinessRatioAttribute()` を想定する
- ただし `null` だけで「未按分」と「混在」を兼ねるのは状態が曖昧なので、表示や判定用途では `business_ratio_state` のような別状態を持つのが望ましい
- 想定する状態は `not_allocated` / `uniform` / `mixed` の 3 つ

## 入口

按分付き登録の正規ルートは既存の `TransactionRegistrar` とする。按分専用の登録サービスは設けない。

- UI・定期取引・改訂入力は、いずれも「分割前の入力 shape」を `TransactionRegistrar` に渡す
- `TransactionRegistrar` が正規化段階で按分を展開し、実際に保存する `journal_entries` を組み立てる
- 展開後は既存のバリデーション・貸借一致検証・保存をそのまま通す

按分ロジックを `RecurringTransactionPlan` や `TransactionRevisor` 側に重複実装しない。

- 新規登録
- 予定取引生成
- 予定取引確定
- 改訂

のすべてが同じ正規化パスを通ることを優先する

### 入力 shape

```php
[
    'sub_account_id' => 123,          // 水道光熱費の補助科目
    'type' => 'debit',
    'gross_amount' => 10000,          // 税込全額
    'tax_type' => 'taxable_purchases_10',
    'business_ratio' => 60,
]
```

初期実装では、`business_ratio` を指定できるのは `gross_amount`（税込全額）入力の借方経費行のみとする。

- `net_amount` 直接入力との併用は初期実装では対象外とし、必要になった時点で整理する
- `TransactionRegistrar` は `gross_amount` 入力の借方経費行に限り、`business_ratio` 未指定なら `100` を補完する
- `net_amount` 直接入力の経費行は初期実装では按分対象外とし、`business_ratio` は `null` のまま扱う
- 改訂や予定取引でも、按分対象行はこの入力 shape に揃える

### 展開ルール

1. 事業分（税込） = `floor(gross_amount × business_ratio / 100)`
2. 家事分（税込） = `gross_amount - 事業分`
3. 事業分は既存の税分解（`splitGrossAmount`）を通し、指定された `tax_type` を付ける
4. `business_ratio = 100` の場合は家事分行を生成しない
5. 家事分がある場合は、`事業主貸 / 家事按分` の補助科目への借方行とし、`tax_type` なし・`tax_amount = 0` とする
6. 事業分の経費行に `business_ratio` を保存し、家事分がある場合は事業分行と家事分行の両方に同じ `allocation_group_id` を設定する

端数は事業分の切り捨てで処理する（納税者有利に倒さない）。取引単位の円未満処理として扱い、テストで固定する。

例: `gross_amount = 10001`, `business_ratio = 60`

- 事業分 = `floor(10001 × 60 / 100)` = `6000`
- 家事分 = `10001 - 6000` = `4001`

### `家事按分` 補助科目の扱い

家事分の受け先として、`事業主貸` 配下にシステム管理の補助科目 `家事按分` を用意する。

- `TransactionRegistrar` が按分展開時に `事業主貸` 配下へ `firstOrCreate` で補完する
- この補助科目はシステム規約に依存するため、将来の補助科目管理でも改名・削除の保護対象とする
- 実装上は、補助科目名を `BusinessUnit` の定数として持つことを想定する

### 消費税の扱い

家事使用分は仕入税額控除の対象外である。

- 事業分だけに課税仕入の `tax_type` が付くため、将来の消費税集計は税区分別に合算するだけで控除額が正しく減る
- 課税事業者・免税事業者（みなし区分）のどちらも、既存の税正規化フローに事業分を通すことで対応する

## バリデーション方針

- `business_ratio` は 1〜100 の整数とする
- `business_ratio` を付けられるのは、expense タイプの勘定科目に属する補助科目の借方行のみとする
- 展開後の仕訳は従来の貸借一致・所属事業体・税区分の検証をすべて通す

## 修正

按分割合の変更は、専用の再計算機構ではなく仕訳修正（`TransactionRevisor` / journal-revision-design.md）に乗せる。

- 割合の変更 = 旧取引の無効化 + 新しい割合で再登録（改訂）
- Revisor の入力も新規登録と同じ `gross_amount + business_ratio` の形を受け付ける
- Revisor は自前で按分計算せず、`TransactionRegistrar` の正規化再利用によって展開を再実行する
- 元の全額は `allocation_group_id` で束ねられた「事業分経費行 + 家事分行」または `business_ratio = 100` の単独経費行から復元できる

したがって、改訂の入力モデルは「保存済み `journal_entries` をそのまま編集する」方式ではなく、「分割前の入力を再解釈して再登録する」方式に寄せる。

- `journal-revision-design.md` 側もこの前提に合わせて更新する
- 少なくとも按分対象行については、改訂 UI / API が raw input を扱えることを前提にする
- ただし初期実装では、`recurring_transaction_plan_id != null` の確定済み取引は改訂対象外のままとし、プラン由来の按分取引は確定後に割合修正できない制約を明記する

## 予定取引・定期取引との関係

- 予定取引も同じ展開ルールで登録されるため、予実サマリー（`FiscalYearSummaryCalculator`）は変更なしで事業分ベースの見通しになる
- `RecurringTransactionPlan` は按分済み仕訳を持たず、分割前入力のテンプレートを持つ
- `RecurringTransactionPlan::toTransactionData()` は按分済みエントリではなく、`gross_amount + business_ratio` を含む raw input を返す
- raw input の展開は常に `TransactionRegistrar` が行う
- `RecurringTransactionPlan` は厳密な税内訳テンプレートではなく、総額ベースのテンプレートとして扱う
- `amount + tax_amount` から `gross_amount` を組み立てた後、正式な `net_amount / tax_amount` は `TransactionRegistrar` の税分解結果を正とする
- 月ごとに割合が変わる場合も、帳簿上の真実は各取引に記録された割合であり、プラン側のデフォルトは生成時の初期値にすぎない

### 予定取引確定

現行の「予定取引の 2 行仕訳を直接上書きする」方式は、按分導入後には採らない。

- 按分後は 1 予定取引が 3 行以上の仕訳を持ちうる
- 確定時だけ別ルールで行編集すると、通常登録と保存形がずれる

そのため、予定取引確定は専用ユースケースとして扱う。

- 入口は `App\Services\PlannedTransactionConfirmer` を想定する
- 予定取引確定の入力も raw input shape で受ける
- 確定時はその入力を `TransactionRegistrar` と同じ正規化ルールで解釈し、仕訳明細全体を置き換える
- `is_planned = false` への遷移はこのユースケースの中で行う
- 既存の `TransactionRegistrar::confirmPlanned()` はこの専用サービスへ統合し、廃止する
- `RecurringTransactionPlan::confirmTransaction()` も専用サービスへの委譲または廃止対象とする

### 並行操作の防止

`PlannedTransactionConfirmer` は DB トランザクション内で対象取引を `lockForUpdate()` 付きで再取得し、次を再検証する。

- `is_planned = true`
- `is_active = true`

いずれかを満たさない場合は例外を投げる。

- 二重確定を防ぐため
- 確定と予定取消（`deactivate()`）の競合を防ぐため
- 確定中に別操作で状態が変わった planned 取引を誤って上書きしないため

予定取引は監査上の確定帳簿ではないため、初期方針では改訂チェーンは使わず、同一 `Transaction` の仕訳明細差し替えで扱う。取消は従来どおり `deactivate()` ベースで扱う。

## 対象外

次は本ドキュメントのスコープ外とする。

- 固定資産の事業専用割合
  - 車両等の按分は年末振替ではなく、`FixedAsset` に事業専用割合を持たせて償却費計上時に事業分だけ経費算入する形が本来であり、固定資産側の拡張として別途扱う
- 補助科目ごとのデフォルト割合設定（入力時のプリフィル）
  - UI の利便機能でありモデル層の正しさに関わらないため、将来拡張とする
- 定期取引計画の複数明細化
  - 初期実装では `RecurringTransactionPlan` の現行前提（単一借方・単一貸方・単一金額）を維持し、その 1 明細に対する `business_ratio` だけを扱う
  - 1 プランに複数の按分対象経費行を持たせる設計は別途扱う
- 月次締めオペレーションの設計
  - 本方式では締めが検証のみになる、という前提だけを共有し、詳細は別ドキュメントで扱う

## 表示方針

- 元帳・集計は従来どおり `is_active = true` の取引を対象にすればよく、按分の特別扱いは不要
- 経費科目の元帳には事業分だけが載り、家事分は `事業主貸` の元帳に載る
- 取引一覧・詳細では `journalEntries` から導出した表示値を使う
- 全按分対象行が同率なら `Transaction::business_ratio` アクセサで「60% 按分」と表示できる
- 複数按分行が混在する場合は `%` を単一値で表示せず、「按分あり」や「混在」などの導出表示を許容する

## まとめ

家事按分は「取引ごとの入力時分割」として扱う。

- 割合は経費行（`JournalEntry`）に記録し、金額は登録時に実仕訳へ分割する
- 入口は `TransactionRegistrar` の正規化層に閉じ、集計サービスには一切手を入れない
- 新規登録・改訂・予定生成・予定確定の入力モデルは raw input shape に揃え、按分展開は `TransactionRegistrar` に一元化する
- 割合の修正は仕訳修正（改訂）の一種として `TransactionRevisor` に乗せる
- 予定取引にも同じ分割が効くため、見通しが事業分ベースになる

この方針により、月ごとの割合変化・後からの修正・予実の正確さを、既存の「状態遷移 + 履歴保持」の流儀のまま実現できる。
